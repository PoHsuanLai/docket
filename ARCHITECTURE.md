# Architecture

docket is the desktop's action layer and the companion that uses it: **typed actions** every app
declares in a manifest, the **router** that is the one decision point for what an agent may do
(Cedar rules, a per-task policy derived from the person's own words, a reviewer that can only
tighten, a breaker, a confirmation only the person can answer), the **MCP edge**, and **the
companion agent**: one identity over many tasks, each its own session, with a working-set
assembler, a roster, side-conversation capture, an idle pass, restart recovery, and **voice**
(hold-to-talk and dictation). The design is the program spec (`SPEC.md` in the agent-spec
folder, which wins where it differs) with the gating research, the persistent-agent research and
the voice area spec; this file is the map of the code that freezes those interfaces.
`CONVENTIONS.md` holds the rules; `FINDINGS.md` the open items and every `todo!()`.

Reading order: section 1 (find the crate), section 3 (find the home), section 4 (find the
trait), section 5 (the gate in one picture), section 6 (copy the recipe).

## 1a. Portable core and desktop extras

The rule (quire design/36): everything except the desktop environment is cross-platform, and
the desktop's features are additive extras that are probed at run time and absent from foreign
builds. For docket that makes two sets.

**Portable core: an in-app agent.** These crates build with `--no-default-features` on macOS and
Windows, reach no `zbus`, `inotify`, `landlock`, `pipewire` or `/proc`, and carry no D-Bus type
in a public signature: `docket-vocab`, `docket-manifest`, `docket-permissions-core`, `companion-model`, `docket-core`, `docket-gate-wire`, `docket-wire`, `docket-skills`, `policy-point`, `action-review`,
`docket-router`, `companion-wire`, `companion-core`, `agent-loop`, `docket-planner`, `docket-tasks` (the companion's task model over any transports, clock and surface), `docket-session` (the durable session record and its resume rules), `docket-checkpoint` (restore points: the rules and the store seam), `docket-provider` (the app side: `IntentProvider`, without its `dbus` feature), `docket-client` (the caller side, `Intents` and `InProcess`, without its `dbus` feature), `docket-fake`, `docket-eval`, `eval-core`,
`docket-models` (the model-backed reviewer and policy writer over any transport), `docket-reader` (the quarantined reader over any transport), `docket-memory` (the memory seam over any almanac-client transport), `docket-inapp` (the host that runs the others inside one app), `docket-host`, `voice-wire`, `voice-loop` and `voice-audio`.
An app that embeds `docket-inapp` gets the whole gate (Cedar policy point, reviewer, breaker,
budgets, the confirm sheet only the person can answer) with no other process.

**Desktop extras: one companion across every app.** `docket-dbus` and `docket-client`'s `dbus`
feature (the transport), `intentd` (the cross-app broker and its audit trail), `companiond` (one
identity over many tasks), `readerd` (the quarantined reader as a process around `docket-reader`), `voiced` (the
microphone), `actions-mcp`, `quire-do` (`docket-cli`), `companion-client`, `docket-settings` (the
settings file the shell's pages write), `docket-ds` (quire's adapter), `docket-testbus`, `docket-accept` and
`docket-live`. cua (computer use) is above docket and desktop only. These light up when
`org.quire.Intents1` answers; a missing one means the in-app path, never an error.

Two kinds of Cargo feature, kept apart. A *platform feature* says what the OS provides (inotify,
PipeWire, `/proc`): named for the thing, off where the OS lacks it. The *app-level desktop switch*
is `quire-desktop`, mapped by implication: a crate with a D-Bus client has
`quire-desktop = ["dbus"]` (default on), and `dbus` stays the transport feature that pulls zbus.
`docket-client` is the one such crate here (`docket-dbus` is the D-Bus layer itself and has no
switch; its `inferd` feature names a transport, not the desktop). A portable build is
`--no-default-features`.

`scripts/check-portable.sh` is the mechanical form: `cargo check --no-default-features` on exactly
the portable list, a `cargo tree` grep for the forbidden crates, and `cargo check --target` for
every cross target rustup already has. `scripts/check-boundary.sh` holds the rows (the portable
rows never list a bus). The seams that have no portable answer yet are the "what is still
missing" list in `FINDINGS.md` (portable-core).

## 5. The gate for one call, in one picture

```
caller (role from the connection) -- permits(role, member) ----------------------- refuse the request
  -> Run.Perform(call)
       arguments checked against the manifest ---------------------------------- BadArgs
       handles resolved, labels kept; SessionSaw and per-sink integrity computed by the router
       facts gathered by the router (`facts`): halt, budget, exact repeat, limit (the person's,
         the assistant's and the floor's: the strongest), taint, the grant; Rust never overrides
         what Cedar rules on them
       gate(): a mapping from the Ruling, nothing more
         Ruling from Cedar (rule-of-two, untrusted-sink, halted, over-budget, repeated, limit-never,
         limit-ask and grant-denied are core forbids no layer can lift; `tainted-always-asks` is a core forbid too; the preset's first-use asks):
           Deny ................. Refuse(code)              (worded from the rule that denied and
                                    the facts: Halted(scope), OverBudget(kind), Denied(Repeated |
                                    Never | NotAllowed); the planner sees only the code)
           Ask .................. Previewing -> Confirming  (the app's dry run; the person answers)
                                    unless a standing grant covers the call and `blocker` finds nothing
                                    never-grantable (untrusted into a sink, outside the task, breaker,
                                    budget, destructive): then the reviewer cascade below runs in its
                                    place, the grant skips only the ask, and its use is audited
           AllowJudged .......... reviewer cascade (Quick, Deliberate, SecondOpinion), tighten():
                                    every planned stage allows -> Run; any Ask or failure -> Confirm;
                                    any Deny -> Refuse
           AllowFinal ........... Run
       Confirming: a receipt only a hardware or shell input can make; voice never answers
       Dispatched -> app Outcome -> journal the undo, audit one record, breaker notes the decision
  breaker: 3 in a row, 10 of the last 50, or one goal with different arguments -> session Paused
           until the person says something
```

**Modes.** A conversation is in Auto or Manual (`Mode`), and the mode is the conversation's own:
`agent.start_mode` says how a new one starts, the shell switches it from the input box
(`Intents1.Session.SetMode`, or the `mode` a turn carries; only the shell and the control centre may,
every other role is refused `NotAllowed`, and a floor that holds Manual answers `Locked`), and
`Session.ModeChanged` says every change. The router reads the mode afresh whenever it prepares a
call, so a switch applies from the next step: a call already waiting on a sheet keeps its sheet.
A session that works for a conversation (a worker, a helper's job, a screen run whose opener named
the task that started it) resolves its mode through its parent at prepare time.

The grid is one preset, `policy/presets/default/grid.cedar`, and the rows select its rules. Settings
holds five rows per mode (`agent.auto.*`, `agent.manual.*`: `inside`, `other`, `send`, `delete`,
`screen`); the router resolves the rows of the call's mode, with the floor's locked rows set to
"asks", and hands them to Cedar as `context.rows` beside `context.mode`. A row that asks is the
absence of a permit; "check" permits `perform_unasked` only, so the call is judged; "runs" permits
both. The defaults equal the old Auto and Manual grids. Auto runs reads without a question, runs an
undoable change inside the task (`inside = runs`), sends other undoable changes to the reviewers
(`other = check`), and asks for anything that sends or deletes (`send`, `delete`); first use asks
only for a change, never for a read, and never for the assistant's own bookkeeping (the Companion
and Memory apps). A screen run asks once at its start (`.Gate.Grant`, "Let it use this app": the one
sheet; `cua.run.start` itself is a read and does not ask) when `screen = once`; the router remembers
the answer on the run's session (`screen_apps`) and a standing grant for the app counts the same, and
each step carries it as the context fact `run` (`allowed` or `not_asked`). The yes also lasts for the
conversation the run works for (`conversation_apps` on the end of its chain of parents): a later run
of that conversation in the same app is not asked again, unless a limit or the floor asks every time;
a new conversation asks again. An undoable step of an
allowed run runs; a step that sends or deletes asks; `screen = each` asks at every change of the run.
Manual's rows all ask, and it reviews nothing silently. The core rules (Never, limits, taint, Rule
of Two, untrusted sinks, halt, budget, mass, the administrator's floor) hold whatever the rows say.
A floor `strictness = "ask_more"` holds every conversation in Manual, and its `rows` lock rows to
"asks". A person's own rule may name `context.mode`. A rule's `@why("...")` is the plain sentence
its sheet shows (`AskReason::Said`).

A message never skips this: a `Request` in a `prov::Message` is evaluated under the receiver's
own task policy and the same pipeline. The label travels with the message and joins into the
receiver's taint; a message across Spaces is delivered and never grants a memory read.

## 5a. Router-filled arguments

A parameter may declare `filled` in its manifest (`docket_manifest::Filled`); the router then fills it
and the caller never gives it. It must be optional text (`validate` refuses anything else), it is
left out of `tool_schema` (so the planner is not shown it), and `check_call` refuses a call that
sends it (`BadArgs` with `ArgFault::WrongType`). Two sources:

- `person_words`: the newest turn the person typed in the conversation the call works for
  (`RouterState::conversation_of` of the caller's session, so a screen run's session reads its
  parent's turn), labelled as the person's own words.
- `own_history`, `kinds = "<pattern>"`: the app's own records about that conversation, read
  through `MemoryLink` as `Entries` in the call's Space (`about` = the conversation thing,
  `docket_session::session_thing`, the one home the session log shares; limit 200, the newest
  200 when there are more). The value is a JSON array of the stored bodies, oldest first, labelled
  with the join of the records' labels, so an untrusted screen label stays untrusted. Memory audits
  its own reads (`Memory.Read`), as it does the recall reads.

Filling happens in `perform_once` (`filled.rs`, after `prepare`, before the app is called),
into `Prepared::filled`, and `Router::invocation` merges it over `request.args`. The sheet, the
digest, the policy and the review therefore see what the caller sent and nothing more. A value that
cannot be had (no turns, memory refuses or fails, no records) is left out; the call still runs.

## 6. Recipes

**Add an action to a built-in provider.** Edit `manifests/org.quire.<App>.toml` (every field
written; names carry the app's prefix; an outbound action declares a recipient or destination
sink; a write without undo is destructive). `docket_manifest::validate` and the router's
`Registry::unresolved` check it in `tests/it/manifests.rs`; add its behaviour to the provider:
`intentd::builtin_memory` for `org.quire.Memory`, `Router::companion_perform` (docket-router,
`companion.rs`) for `org.quire.Companion`. `HostedLink` routes the two names to them.

**Add a member to `Intents1`.** (1) A variant of `IntentsRequest` and its reply in
`docket-wire`; (2) its row in the `members!` list (`Member`, `IntentsRequest::member`); (3) its row in `docket-router::auth`
(who may call it, and a test that names the guarantee); (4) the method in `docket-dbus`'s table
for its interface; run `cargo test -p docket-dbus`, which prints the new XML; replace
`dbus/org.quire.Intents1.xml` with it in the same commit; (5) a method on `docket_client::Intents`.

**Add a Cedar rule.** Write it in `policy/presets/default/grid.cedar`, keyed on `context.rows` where a mode's row should decide it (or `policy/core.cedar` for a safety invariant that must hold in every mode) with a unique `@id`; `Pdp::load` validates it
strictly against `policy/quire.cedarschema`; add the row to `policy-point/tests/it/grid.rs`. A rule
that tightens only is a forbid; the assistant and administrator directories may only forbid (the loader refuses a permit there).

**Add an action to every face.** Declare it in the app's manifest (recipe above) and implement it in the app's `IntentProvider`. That is all: `quire-do <app> <action>` (`docket-cli`), the MCP tool (`actions-mcp`) and the D-Bus `Run.Perform` are generated from the declaration. An app's menu command or shortcut that is the face of the action names it in `<AppName>.ui.toml`; `scripts/check-intents.sh` fails the app's gate for a menu command with no action that is not listed UI-only.

**Declare a relation.** A planner never reads untrusted content, so when an action needs a thing of
another kind than the one it holds (the sender of a thread, the owner of a file) the app declares it
on the kind: `[[entities.relations]]` with `name`, `label`, `to` (a kind), `many` (`one` or `many`)
and `trust` (`third_party` when somebody else's words decide the answer, else `app_authored`). That
is all the manifest says: `validate` derives the read action `<kind>.related` (one thing of the kind,
a required `relation` choice, classes of both kinds, result the things named), the app implements it
in `Perform` like any action, and the planner reaches it as `quire_related {"of": ..., "relation":
...}`, offered only while some action in its view resolves a relation. The router checks the answer
names things of the relation's kind (no more than `many` allows) and joins the relation's `trust`
and the labels of the handles it was asked from into the label, so an app cannot make a sender
trusted. A recipient taken from the answer meets the same sink rules as any untrusted recipient.
Tests: `tests/it/related.rs` in docket-router (over `docket-fake`'s mail and files).

**Add a red-team case.** A TOML file under `eval/<corpus>/`, in the format documented in
`eval-core/src/case.rs`: the person's turns, the world, the scripted calls and messages of a
hijacked or naive planner (each argument says where it came from), and one `Expect`. Every case
carries a `why`. `corpora_parse` loads them all.

**Add a restore-point store.** Implement `CheckpointStore` (docket-checkpoint) over the storage; it must
never touch the person's own history or, but for `apply`, the files, and `apply` must refuse a plan whose
digest is not the one confirmed. Run `docket_checkpoint::contract::run` from its test (feature `testing`)
over a `Workbench` of its own: that is the whole definition of a store. The data a store returns is
`docket-core::checkpoint`; what it decides (`decide`, `retention`, `next_id`, `plan_restore`) stays pure
in docket-checkpoint, so two stores cannot disagree on it.

**Add a setting.** A field of `AgentConfig` with its default, a row in `SETTING_ROWS` and an arm
of `AgentConfig::value`; the test that pins the rows to the defaults fails until all three agree.
The design/22 row and the sill key are the other repos' agents'.

**A coding agent as the assistant's model (the third choice).** Beside the models inferd runs
(cloud, local), the person may pick an outside coding agent for the assistant: the word
`agent/<program>` in inferd's `ai.model.text.<tier>` (the text slot only; Automatic's pool never
holds one). The contract across the repos:

- **porter owns the word and the refusal, not the agents.** inferd checks the word's shape
  (`ModelRef::agent`, `AGENT_ACCOUNT`) and refuses it for any other slot and for the pool. A
  session whose pick names an agent ends `Unavailable` with a `Declined` event whose reason is
  `DeclinedBecause::AgentChosen`; that is not a failure but the instruction to hand the turn over.
- **docket owns the agents** (`agents.toml`, `agent.acp.agents`). Which `agent/<program>` words
  exist, and whether each can be chosen, is read by Settings from `docket-settings`
  (`read_agents`, `Source::Own { installed }`, `SignInState`, `find_known`/`unlisted` for programs
  found on `PATH` that no entry runs); detent lays those words over inferd's described rows
  (`coding_agents::with_agents`) in a group "Coding Agents", each greyed with a plain reason ("Not
  installed", "Sign in to X first", "Turned off", "Not set up yet"). Picking a turned-off one asks
  to turn coding agents on in the same dialogue. inferd's picker never needs docket's files.
- **companiond does not plan the turn.** `plan_turn` meets the `AgentChosen` decline and calls
  `Companion::hand_over`: the person's own turn (the one the shell recorded) goes to the host
  through the `Handoff` seam (`docket-tasks`); the agent's words are the reply, the route names it
  ("Answered by Claude Code (you chose it)"), a host that refuses ends the turn as a model that
  cannot answer does (`NoModel` for turned off / not set up, so the picker opens, else words).
  `companiond::HostLink` is the bus side (`org.quire.AgentHost1`: `HandOver` starts a turn and
  answers its id; `Wait` is asked again until it answers the `HandReply`, because a turn outlasts
  what the bus lets one call wait).
- **The host is `docket-agent --serve`** (`docket-acp-bin::agent::serve`), a service the bus
  starts for `org.quire.AcpAgent` (`dist/docket-agent.service`, `dist/dbus/org.quire.AcpAgent.service`).
  It, not companiond, opens the agent's session at the router, as the `acp_agent` role: the rule in
  `opening.rs` that only that role may open an outside session is unchanged, and companiond gains
  no way to open one. The only thing companiond can ask of it is a turn, and only companiond may
  (`acp-callers.toml`). It builds the same wiring as the terminal command (`agent::wire`), one
  agent's session at a time, in a folder of the agent's own under the data directory (never the
  home folder), and ends after ten quiet minutes; a turn for another agent ends it and the next
  call starts it again. Sheets, policy, grants and `actions-mcp` are exactly those of
  `docket-agent` on a terminal.
- **The agent apps that are helpers run in the same host.** companiond is not their host, for the
  same reason: only the `acp_agent` role may open an outside agent's session, so `companiond`
  (`AppsLink`) carries the board's `AgentApps` calls over `AgentHost1.AppsBegin` / `AppsWait`
  (`companion_model::helper::{AppsAsk, AppsReply}`, JSON; a job outlasts one bus call, so it is begun,
  then waited for again), and `docket-agent --serve` answers them with `HelperAgents`
  (`agent::helper_host`): one agent process per helper, in a folder of the helper's own under
  `helpers/` in the data directory, over the pseudo-app served once (`agent::live`, shared with
  the assistant's session). It holds the host for one kind of use at a time: while the assistant's
  coding agent has a turn running a helper's job fails as "busy", and the other way round. Which
  app a helper runs, and where its command is, come from `agents.toml`; an app not in it, one
  whose command is not there, and coding agents turned off are each said in plain words. The
  host ends the helpers' agent processes when a helper is removed, when the daemon that asked
  has left the bus, and after ten quiet minutes with no job running. This one-use-at-a-time
  limit and the lack of the desktop's actions for these agents are open (FINDINGS.md).

**Add a machine.** A pure `(state, input) -> (state, effects)` in `agent-loop` or `voice-loop`,
every type `Serialize + Eq`, a table test, and the effects carried out by a daemon.

## 7. Repo rules

- Licence `MIT OR Apache-2.0`; edition 2024; `unsafe_code = "deny"`; `rust-toolchain.toml` pins
  1.98.1 and `deny.toml` is the licence gate.
- Cross-repo dependencies are git dependencies at pinned revs (porter, almanac, stoker, quire), so a plain
  clone builds with no sibling checkout. The pins use the same URL and rev as the other repos' pins of the
  same crates, or cargo links two copies. Local cross-repo work overrides a pin with a `[patch]` (FINDINGS.md).
  External versions are copied from quire's `docs/workspace-deps.toml`, never chosen here.
- Behaviour is `todo!()` behind frozen signatures, each listed in `FINDINGS.md`; shape tests
  (round trips, pinned JSON, introspection, tables) pass.
- Tests never touch the real system: no real bus, no real apps, no GPU, no real engine, no network.
  intentd, companiond, readerd and voiced serve; the first three have a binary test on a private bus, and voiced's `start` is tested on one over a scripted device (the real PipeWire device is `dev/voice-capture-try.sh`, by hand).
- The gate, with every exit code checked (`scripts/gate.sh` runs exactly this):

  ```bash
  set -euo pipefail
  cargo fmt --all --check
  cargo clippy --workspace --all-targets --all-features -- -D warnings
  cargo test --workspace --all-features
  cargo test -p policy-point -p eval-core -p docket-eval
  ./scripts/check-boundary.sh
  cargo deny check licenses
  echo "GATE GREEN"
  ```

  No crate is excluded: every crate builds and tests without hardware or network. (`voice-pipewire`
  links libpipewire but opens no device in a test, and `speech-vad-silero` is not a dependency, so
  neither needs the exclusion `recall-fastembed` needs in almanac.)

## 8. Install

`scripts/install.sh` installs the daemons, the units with their `<unit>.service.d/sandbox.conf`
drop-ins, the D-Bus activation files and interface XML, the settings schema, skills, the policy presets (`policy/presets` to `share/quire/permissions`), default
configuration and the caller tables (`dist/*-callers.toml` go to `/etc/quire`). Flags:
`--prefix DIR` (default `/usr/local`), `--destdir DIR` (for packages), `--user` (under `~/.local`,
no root), `--no-build`, `--bin-dir DIR` (programs built elsewhere), `--dry-run` (print every
action), `--sandbox auto|on|off`, `--distro debian|fedora|arch` and `--with-voice`. Root steps use
`$SUDO`, else sudo, doas or pkexec, else they are printed. The sandbox keys that need a mount
namespace live only in the drop-ins; `auto` tests whether `systemd --user` can use them and leaves
them out where it cannot (Ubuntu 24.04+ by default). `dist/install-dev.sh` is still the way to
install the whole agent stack, with porter and almanac, for one user. The build runs from `/` with `--manifest-path` and the pinned toolchain, so it is linked by the system's own linker; clang and mold (the repo's `.cargo/config.toml`) are for working on the code, and an install never needs them.
